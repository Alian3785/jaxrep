# Проверки актуальной среды

## Chex

[Chex](https://github.com/google-deepmind/chex) 0.1.92 уже входит в закреплённый
runtime проекта. Дополнительная установка из GitHub не нужна: штатный
`bash scripts/install_runtime.sh` устанавливает эту версию вместе с JAX.
На 8 октября 2026 импорт проверен в `/home/minigrid/.venvs/numbergrid-cuda13`.

`stoix/tests/number_grid_chex_test.py` проверяет текущую среду:

- `chex.variants` запускает CUDA-проверки под `jit`;
- результаты `vmap(step)` сравниваются с отдельными шагами для перемещения,
  атаки, ожидания, защиты, хода ИИ, побега, запрещённого действия и конца эпизода;
- формы, типы и конечность значений проверяются на всём дереве состояния/TimeStep;
- целочисленные поля, булевы флаги и PRNG сравниваются точно, вещественные — с допуском;
- общие фикстуры сохраняют JIT-функции и нормализуют типы входов, чтобы изменение
  значений не вызывало повторную компиляцию всего боя.

Все эти проверки находятся в тестах, вне learner. Изменение размеров карты или
наблюдения закономерно требует новой компиляции и не считается ошибкой этой проверки.
Chex проверяет свойства JAX-кода, а ожидаемые игровые правила задаются независимыми
сценариями. Совпадение `jit` с обычным вызовом само по себе не доказывает верность механики.

```bash
bash scripts/run_gpu.sh scripts/test_gpu.py --output results/gpu-tests/RUN
bash scripts/run_gpu.sh -m pytest -q stoix/tests/number_grid_chex_test.py
```

Все тесты проекта запускаются только на GPU через `scripts/run_gpu.sh`.
Корневой `conftest.py` требует CUDA до сбора тестов: CPU-backend запрещён,
отсутствие GPU завершает запуск с ошибкой. Подготовка состояний и вызовы JAX
без `jit` также используют GPU; это не CPU-backend.
Полный прогон, включая запуск, фикстуры и компиляцию, должен укладываться в 15 минут;
при превышении сначала оптимизируем медленные проверки, затем убираем малоценные
или дублирующие, сохраняя проверки основных механик и известных регрессий.
В GitHub Actions на стандартном runner выполняется только Ruff; тесты там не запускаются.
Штатная команда: `bash scripts/run_gpu.sh scripts/test_gpu.py --output results/gpu-tests/RUN`.
Все группы идут в одном CUDA-процессе, без параллельных GPU-задач. Обычный полный
прогон сохраняет исполняемые файлы JAX в `results/gpu-tests/compilation-cache`:
повторное использование компиляции не пропускает исполнение тестов. Изменённые
вычисления JAX компилирует заново. Для отдельного замера с пустым кешем используется
`--cold-cache`; оба режима подчиняются лимиту 15 минут. Режим кеша и время команды
сохраняются в `results.json`, длительности тестов — в `junit.xml`.
После ошибки сначала проверяется конкретное исправление; полный набор не нужно
запускать заново после каждой мелкой правки. Таблицы механических случаев
переиспользуют скалярные исполняемые функции; отдельные Chex-проверки и тесты
двойников/призывателей сохраняют сравнение с `vmap`.
Сценарии массовых атак используют общую неизменяемую фикстуру. Для строительства
других фракций постоянный режим карты исключает компиляцию неиспользуемой ветви
боя; полный переход с отклонением действий в бою проверяется для Легионов.
Отдельный случайный scan с проверкой только конечности значений удалён как
дублирующий: сохранены точное сравнение пакетных/скалярных шагов, проход всей
карты, градиент PPO и предметные регрессии.

9 октября 2026, после добавления всех зелий: 314 тестов прошли за **9 мин 38 с**
с сохранённым кешем и за **14 мин 53 с** с пустым кешем, включая запуск из Windows.
Внутри pytest — 8 мин 43 с и 13 мин 29 с соответственно. Результаты:
[validation/potion-performance.json](validation/potion-performance.json).

## Лимит тестового обучения и замеров

Тестовое обучение на GPU и проверочный замер полного learner ограничены
**1 000 000 переходов на запуск суммарно по всем параллельным средам**.
Это предел обучения, а не число переходов на каждую среду. Не продолжать один
длинный тестовый запуск серией коротких для обхода ограничения. Целевое обучение
на большем бюджете выполняется отдельно по явному запросу пользователя.

```bash
bash scripts/run_gpu.sh benchmark_number_grid.py --test-run --total-timesteps 1000000 --output results/test-learner/RUN --wandb-mode disabled
```

В режиме `--test-run` бюджет по умолчанию равен 1 млн; превышение отклоняется
до инициализации CUDA и логирования. Pytest автоматически включает этот режим
через `NUMBERGRID_TEST_RUN=1`, который наследуют дочерние процессы.
`--smoke` сохраняет бюджет 250 тыс. Пакетный скрипт
`scripts/run_unit_action_stage.py` также запускает только проверки по 1 млн;
его старые результаты на 5/20 млн остаются историческими и не сравниваются
с новым бюджетом как эквивалентные замеры.

Полный набор механических тестов не запускает полное PPO-обучение: интеграция
политики проверяется вычислением градиента, маской действий и auto-reset.
Проверки ограничителя также не обучают модель.

## Ускорение фикстур

Повторные расчёты reset, подготовки боя, наблюдений, характеристик и маски
используют стабильные JIT-функции общих неизменяемых сред. Подготовка и обрезка
пакетов состояний выполняются двумя небольшими JIT-функциями для всего дерева,
вместо отдельных GPU-запусков для каждого поля. Большой переход остаётся отдельной
скомпилированной функцией: разное число случаев не перекомпилирует весь бой.
В проверке регенерации и мгновенного побега с полным каталогом предметов JIT
возвращает только проверяемые поля; сам шаг вызывается без подмены правил.
Проверки механик и сравнение scalar/vmap сохранены.

9 октября 2026 полный CUDA-набор после оптимизации: **341 тест прошёл за 8 мин 41 с**
с учётом запуска из Windows; предыдущий успешный набор занимал **11 мин 02 с**.
Сокращение полного времени — **21,3%**. Внутри pytest: 7 мин 50 с вместо 9 мин 58 с.
Все 337 прежних сценариев сохранены; добавлены четыре проверки лимита обучения.
Оба результата получены с постоянным кешем; это сравнение сохранённого исходного
прогона и итогового, а не замер с пустым кешем. Компиляция включена во время тестов

## Как использовать тесты Python-референса

Источник: `C:\Disciples 2 python reference\Big_map`. Проверено 8 октября 2026:
`run_tests.py --collect-only -n 0 -p no:cacheprovider` собрал **8474 сценария в 66 файлах**
папки `tests/`. Это именно сбор, не отчёт об успешном выполнении всех тестов.
Ещё 11 файлов `test_*.py` лежат непосредственно в `Big_map` и не входят в этот запуск.
Большое число сценариев получается из параметризации: расстановок, сторон, типов
юнитов и граничных значений. Они описывают гораздо больше механик, чем текущая JAX-среда.

### Практический способ переноса

1. Для каждой механики выделять из тестов условия и независимый ожидаемый результат.
   Составить реестр: исходный `nodeid`, механика, поддерживается ли она в JAX, целевой
   тест, намеренное расхождение. Считать покрытие механик и граничных случаев, а не
   только общее число тестов. Нереализованные механики хранить в плане, не маскировать
   тысячами пропущенных тестов или `xfail`.
2. Сделать небольшой адаптер состояния: Python-позиции 7–12 героя соответствуют
   JAX-слотам 0–5, позиции 1–6 врага — слотам 6–11. Переводить действия по смыслу,
   а не по их числовым индексам. Python может автоматически выполнить несколько
   ходов ИИ в одном `step`, а JAX выполняет один ход бойца: сравнивать состояние
   после одинакового набора действий, а не после одного вызова каждого API.
3. Для случайных механик подавать одинаковые **броски**, а не просто одинаковый seed:
   `random.Random` и JAX PRNG дают разные последовательности. Фиксировать попадания,
   прибавки урона, выбор цели и очередь; отделять тест распределения случайности от
   детерминированного сценария. Сравнивать HP, нанесённый урон, доступные цели, статусы
   и окончание боя. Награды и наблюдения сравнивать только там, где их смысл совпадает.
4. Запускать Python-референс отдельным процессом в его собственном окружении. Сначала
   проверять исходные тесты выбранного поднабора, затем сохранять небольшие JSON-фикстуры
   вида «исходное состояние → действия/броски → ожидаемый результат». Добавлять исходный
   `nodeid` и хеш референса, получившего результат. Обычные JAX-тесты и CI смогут читать
   фикстуры без локального диска C:, PyTorch и зависимостей Python-проекта. Ожидаемые
   ответы не генерировать самой проверяемой JAX-реализацией и не обновлять автоматически
   при падении теста.
5. Прогонять перенесённые сценарии в обычном режиме, под `jit` и пакетно под `vmap`.
   Большие матрицы удобно проверять пакетами; при сбое выводить исходный `nodeid`,
   действие и конкретное поле расхождения. Дополнять инвариантами: HP неотрицательно,
   погибший не ходит, запрещённое действие не атакует, ожидание доступно один раз.

Инициативу и ожидание не следует слепо копировать: по требованию пользователя они
должны приближаться к оригиналу и намеренно отличаются от Python. Такие расхождения
нужно явно фиксировать, проверяя правило по первичным источникам. Найденный в референсе
баг тоже не становится обязательным поведением JAX. Неподтверждённые случаи проверяет
пользователь в оригинальной игре или IDA согласно `AGENTS.md`.

Начать стоит с двух первых файлов: маленький адаптер, ограниченный поддерживаемыми
атаками и расстановками, даст проверку актуальных механик без переноса всей архитектуры
Python. Сохранять старые JAX-реализации ради этих проверок не требуется.

Торговец и тренер: `stoix/tests/number_grid_sites_test.py` включён в полный CUDA-набор. Для этой задачи требуется отдельное разрешение на GPU согласно AGENTS.md; статические проверки не заменяют исполнение тестов.
